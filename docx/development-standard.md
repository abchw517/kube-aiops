## 打开与交付原型

浏览仓库目录时，原型入口和场景 HTML 之间使用相对路径。克隆仓库或解压 GitHub 下载的完整仓库后，用浏览器打开各模块的 `prototype.html`。GitHub 源码页面用于查看文件内容。

单独交付或分享原型时，从仓库根目录运行以下命令，生成一份全站原型和五份模块独立 HTML。全站文件 `kube-aiops-full-portal-prototype.html` 从登录进入五个模块。各模块文件包含场景目录及实现依据。

```bash
python3 scripts/package-prototypes.py /tmp/kube-aiops-prototypes
```

下载生成的任意一份 HTML，用启用 JavaScript 的浏览器直接打开。每个 HTML 场景都要有与用途对应的交互。交付前在浏览器中逐个打开独立 HTML 的场景，至少执行一项该场景的实际操作，并确认有可观察的结果，例如筛选后的列表、打开的详情、弹窗、表单反馈或更新的选中状态。仅能切换到场景或看到页面内容不足以通过交互验收。业务行为有歧义时，核对相应应用源码，并在原型中给出代码入口。可用 `--source-ref <已发布的提交 SHA>` 固定原型里的代码依据。原型内的账号、诊断、配置和写入结果均为演示数据。

## 更新规则

产品设计交付维护在以上五个目录。子功能、改版和版本迭代一律原地更新归属模块的现有章节和 HTML。跨模块需求按职责修改涉及模块的对应章节，相互引用。数据源配置归资源管理，诊断侧的查询、统计和展示归诊断控制台。登录页面归前端 UI，认证与会话规则归系统管理。

同一功能有多版时，从目标分支最近确认或交付的文件取现行规则，按功能和交付类型合并。旧文档中仍有效的接口、权限、数据范围和测试边界并入现有章节，旧版本原文由 Git 历史追溯。现行规则、历史验收和待交付设计应当写清适用阶段。

一个模块固定维护以下七份文档和一个交互原型入口。更新原型时直接维护入口所指向的稳定 HTML 页面及必要静态资源，跨模块共用一个原型时从各模块入口链接到相应起始页面。只有新增独立的产品一级模块时，才新增模块目录和相同的交付结构。

| 文件 | 交付要求 |
| --- | --- |
| `design.md` | 设计方案。记录范围、关键决策、数据和权限边界、接口与原型入口。 |
| `00-prd.md` | 产品需求。记录目标、用户、范围、优先级与可观察的验收标准。 |
| `01-pages.md` | 页面拆解。记录入口、布局、操作、权限及加载、空、错误等状态。 |
| `02-features.md` | 功能拆解。记录触发、输入输出、业务规则和相关页面。 |
| `03-user-stories.md` | 用户故事。记录角色、目标、场景及验收条件。 |
| `04-development-tasks.md` | 开发任务。记录依赖、代码落点、完成条件与对应测试。 |
| `05-unit-test-cases.md` | 测试用例。记录夹具、操作、预期，覆盖单元、集成、浏览器和现场验收。 |
| `prototype.html` | 原型入口。链接当前可点击的 HTML，覆盖模块主要路径。 |

部署说明、架构、基线和阶段验收由 `docx/` 根目录继续维护。

## 编号和追踪

使用 `<模块前缀>-Pxx → Fxx → USxx → Txx → UTxx`。允许一对多及多对多关联。编号在模块内保持稳定。工程子任务可加 `-A`、`-B`，细化测试可加 `-01` 等序号。跨文档使用相对链接定位条目。

## Coding 执行顺序

1. 页面拆解以当前 PRD 为输入，梳理导航、数据范围和状态。功能拆解补齐各页动作及跨页业务规则。
2. 每个功能写出用户故事和可观察的验收标准。每个故事对应开发任务，列清依赖和编码前需要确认的边界。
3. 开发前识别要覆盖的单测并记录预期。新增或变更 API 时同步契约及使用方。开发时优先沿用目标分支的服务、授权、持久化及前端入口。
4. 完成任务后运行其单测和受影响回归。外部系统的真实调用、存储事务和浏览器链路另做对应的集成或端到端验证。记录执行结果，并在 PR 描述中列出覆盖的故事和任务编号。
5. 需求变更时追踪下游受影响页面、功能、故事、任务及用例。评审项写明具体影响和当前约定，明确未决分支后推进可独立交付的任务。

## 提交前检查

- 需求有对应页面或后台能力，页面有对应功能，功能的故事有任务和测试。
- 每个测试能追到可观察的验收标准。成功、无权限、无数据、失败恢复和已知边界按实际功能覆盖。
- 测试结果与试点验收状态如实记录。文档和实现使用相同术语及状态含义。
